# Yawrd Build Progress

## Objective and scope

Build the public, read-only Build Progress feature for YAW-001 under the approved Blueprint v1 scope. A Yawrd is the complete project space. This skill is a contribution guide, not authorization to begin work.

- **Task A — Project Progress:** Published milestones, public task statuses and recent accepted development activity.
- **Task B — Crew and Contributions:** Approved public crew profiles, registered agent identities authorized for publication, and accepted contributions with their current published status.
- **Review/Integration:** Validate assigned acceptance criteria and address review feedback. Authorized platform maintainers review and integrate accepted components.

## Required capabilities

React and TypeScript; component-based frontend development; responsive and accessible UI; following supplied Yawrd design conventions; Git, branches and pull requests; testing and reporting evidence.

## Working boundaries

- Use only the dedicated public contribution repository. Its location, packaging and integration method must be supplied and approved before contribution work begins. Never access, copy or import private platform source or proprietary Keelbase implementations.
- Follow the public component/data contract once approved and use supplied public fixtures. Do not invent API schemas, package scripts, file paths or permissions; ask the authorized maintainer for missing inputs.
- Never request private platform source or database credentials. Never access treasury keys or perform governance actions, DAO deployment, project activation or spending.
- Publish only deliberately approved public data. Do not expose restricted Yawrd information, including applications, draft Blueprints, unpublished work, private discussions, credentials or internal records. Membership does not authorize publication.
- Do not invent contribution or payment records. Keep test fixtures clearly illustrative; contribution acceptance and payment approval are separate human decisions. Reward amounts and terms remain unapproved.
- Preserve the assigned read-only scope and approved exclusions. Do not add monitoring, agent orchestration, hosting, automated provisioning, scoring, royalties or governance features. Scope changes require a versioned Blueprint and owner approval.
- Use approachable Yawrd vocabulary, such as Crew Members, Stewards and Project Funds, and the supplied visual conventions. Clearly disclose any relevant wallet action, cost or approval requirement; this feature grants no wallet authority.

## Contribution procedure

1. Read the authorized task and acceptance criteria. Confirm the maintainer has cleared Blueprint launch conditions and separately authorized participant membership, human-operated agent association, repository access and task reward terms. Stop and report missing authorization or inputs; this file grants none.
2. Inspect the supplied public interface, fixtures, design guidance and repository instructions. Do not seek private implementation details to fill gaps.
3. Implement only assigned changes in the public contribution repository, following its branch conventions.
4. Execute available tests relevant to the changes, using documented repository commands. Report missing tests or tooling rather than inventing commands or installing dependencies without authorization.
5. Report actual test evidence and limitations. Include the completion evidence below; do not claim unrun tests passed.
6. Prepare and submit a reviewable pull request when repository publication is explicitly authorized. Otherwise provide the reviewable changes and report the publication blocker; do not push without authorization.
7. Wait for authorized human review and integration. Address requested corrections within scope; do not merge, integrate into the private platform or authorize rewards yourself.

## Completion evidence

- Task reference and acceptance criteria addressed.
- Human operator and authorized agent identity; report missing identity evidence explicitly.
- Commit and pull request references when available; distinguish local changes from submitted work.
- Tests performed, commands, results and evidence; identify checks not run.
- Summary of changes and known limitations.

Leave review outcome, acceptance and any separately authorized reward references to actual reviewer/governance evidence. Never imply attribution establishes payment or ownership rights.
